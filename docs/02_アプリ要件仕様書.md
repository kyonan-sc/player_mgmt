# 境南SC 選手評価管理システム — アプリケーション要件仕様書

## 1. 概要

### 1.1 アプリケーションの目的

少年サッカーチームに所属する選手の能力を定期的かつ客観的に評価し、選手一人ひとりの成長を可視化する。

評価結果をもとに、適切なチーム編成、練習メニューの検討、個別指導を行うための判断材料を提供する。

主観的な印象や直近の試合結果だけに依存せず、継続的な記録と共通の評価基準に基づいた指導を可能にする。

### 1.2 対象

- 境南SC所属選手
- 初期導入対象：小学3年生
- 将来的に他学年へ展開可能とする

### 1.3 利用者

- チーム管理者
- 担当コーチ
- 閲覧権限を持つチーム関係者

選手本人および保護者向けの画面は初期リリースの対象外とする。

### 1.4 基本コンセプト

- 選手の現在の能力を把握する
- 選手の過去から現在までの成長を把握する
- 選手ごとの強みと課題を明確にする
- 複数コーチ間で評価基準を共有する
- 客観的な評価に基づくチーム編成を支援する
- チーム全体の育成状況を把握する

評価結果は選手の固定的な能力や将来性を決めるものではなく、評価時点における観測結果として扱う。

## 2. 基本的な運用フロー

1. 管理者が選手およびコーチを登録する。
2. 管理者が評価期間を作成する。
3. 対象選手、評価基準、必要評価者数を設定する。
4. 評価期間を開始する。
5. 各コーチが選手を独立して評価する。
6. コーチが評価を提出する。
7. システムが評価結果を集計する。
8. 管理者が評価状況を確認する。
9. 評価を確定する。
10. 評価結果に基づくA/B/Cチームの推奨編成を表示する。
11. コーチ間で協議し、実際のチーム編成を決定する。
12. 次回評価期間に同様の評価を実施する。

評価は4〜6週間に1回程度を推奨する。

実施間隔はシステムによって強制せず、任意のタイミングで評価期間を作成できるものとする。

## 3. 評価制度

### 3.1 評価カテゴリ

評価は4カテゴリ、9項目、100点満点とする。

| カテゴリ                 |  配点 | 評価項目数 |
| ------------------------ | ----: | ---------: |
| 技術力 / Technique       |  30点 |          3 |
| 判断力 / Decision Making |  25点 |          2 |
| 対人能力 / Duel          |  25点 |          2 |
| 試合関与 / Involvement   |  20点 |          2 |
| 合計                     | 100点 |          9 |

### 3.2 評価項目

| ID     | カテゴリ | 項目       | 評価内容                                     |
| ------ | -------- | ---------- | -------------------------------------------- |
| TEC-01 | 技術力   | トラップ   | ボールを意図した位置にコントロールできるか   |
| TEC-02 | 技術力   | ドリブル   | ボールを保持しながら移動・方向転換できるか   |
| TEC-03 | 技術力   | パス       | 味方に適切な強さ・方向でパスを出せるか       |
| DEC-01 | 判断力   | 状況認識   | 味方、相手、スペースを認識しているか         |
| DEC-02 | 判断力   | プレー選択 | 状況に応じた適切な行動を選択できるか         |
| DUE-01 | 対人能力 | 攻撃1対1   | 相手を突破する、またはボールを保持できるか   |
| DUE-02 | 対人能力 | 守備1対1   | 相手の突破を防ぎ、ボールを奪う行動ができるか |
| INV-01 | 試合関与 | 攻撃参加   | ボールを持っていない場面でも攻撃に関与するか |
| INV-02 | 試合関与 | 守備参加   | ボールを失った際に守備へ切り替えられるか     |

### 3.3 評価段階

各項目を1〜5点の5段階で評価する。

| 評価 | 定義                                           |
| ---: | ---------------------------------------------- |
|    1 | 基本的な実行がまだ難しい                       |
|    2 | 補助や指示があれば実行できる                   |
|    3 | 基本的な状況で自力で実行できる                 |
|    4 | 試合中でも多くの場面で実行できる               |
|    5 | 試合中に安定して実行し、状況に応じて応用できる |

未観測は1点とは区別する。

十分な観察ができていない項目は未評価として扱い、評価者が推測で点数を入力することを要求しない。

### 3.4 項目別評価基準

以下を初期評価基準とする。

| 評価項目   | 1点の目安                          | 3点の目安                              | 5点の目安                                      |
| ---------- | ---------------------------------- | -------------------------------------- | ---------------------------------------------- |
| トラップ   | ボールを止めることが難しい         | 基本的なパスを止められる               | 次のプレーを意識したコントロールができる       |
| ドリブル   | ボールを頻繁に失う                 | 基本的な移動や方向転換ができる         | 相手やスペースに応じて速度と方向を変えられる   |
| パス       | 味方へのパスが安定しない           | 近距離の味方にパスを出せる             | 状況に応じて方向、強さ、タイミングを調整できる |
| 状況認識   | 主にボールだけを見ている           | 周囲を確認する場面がある               | 受ける前から周囲を確認し続けている             |
| プレー選択 | 状況に関係なく同じ行動をする       | 基本的な状況で適切な選択ができる       | 複数の選択肢から状況に応じて判断できる         |
| 攻撃1対1   | 相手に対応できず失うことが多い     | 相手をかわす、または保持することがある | 相手の動きを見て突破や保持を選択できる         |
| 守備1対1   | 相手への対応が難しい               | 相手に寄せて突破を妨げられる           | 距離や方向を制御し、適切な機会に奪える         |
| 攻撃参加   | ボールを持たない場面で動きが少ない | パスを受ける動きができる               | スペースを作る、サポートする等の動きが継続する |
| 守備参加   | ボールを失った後の反応が少ない     | 守備へ切り替えられる                   | 素早く切り替え、味方と連携して守備できる       |

2点および4点は隣接する評価段階の中間として扱う。

評価基準は評価入力画面から常に参照可能とする。

### 3.5 評価方法

以下のような共通の観察機会を設ける。

| 評価項目   | 推奨観察方法                         |
| ---------- | ------------------------------------ |
| トラップ   | 一定条件のパス受け、およびゲーム形式 |
| ドリブル   | 共通ドリブル課題、およびゲーム形式   |
| パス       | ペアパス、ゲーム形式                 |
| 状況認識   | 3対3、4対4等のミニゲーム             |
| プレー選択 | ミニゲーム、通常の試合               |
| 攻撃1対1   | 1対1の攻撃課題                       |
| 守備1対1   | 1対1の守備課題                       |
| 攻撃参加   | ミニゲーム、通常の試合               |
| 守備参加   | ミニゲーム、通常の試合               |

単一の成功・失敗のみで評価を決定せず、複数回のプレーを観察する。

できる限り全選手について同等の観察機会と評価条件を確保する。

得点数や勝敗のみで評価を行わない。

## 4. 評価計算仕様

### 4.1 カテゴリ得点

カテゴリ得点は以下の式で計算する。

カテゴリ得点 ＝ 項目得点の平均 ÷ 5 × カテゴリ配点

技術力の評価が以下の場合：

- トラップ：4
- ドリブル：5
- パス：3

平均は4となるため、技術力の得点は24点となる。

### 4.2 総合得点

4カテゴリの得点を合計する。

総合得点 ＝ 技術力得点 ＋ 判断力得点 ＋ 対人能力得点 ＋ 試合関与得点

得点範囲は20〜100点とする。

内部計算では途中の丸めを行わず、最終的な総合得点を小数第1位に丸める。

チーム判定には表示される総合得点と同じ値を使用する。

### 4.3 複数コーチによる評価

同一の選手を複数のコーチが評価できるものとする。

各評価項目について、提出済み評価の算術平均を計算する。

集計対象となる評価者の重みは等しくする。

下書きおよび未提出の評価は集計対象外とする。

評価提出には全9項目の入力を必須とする。

必要評価者数の初期値は2名とし、評価期間の作成時に変更可能とする。

必要評価者数に達していない選手は評価不足として扱う。

### 4.4 評価者間のばらつき

同一項目における最大評価と最小評価の差が2点以上の場合、評価のばらつきが大きいことを表示する。

管理者は評価確定前に該当項目を確認できるものとする。

ばらつきがある評価を機械的に除外しない。

## 5. A/B/Cチーム判定

### 5.1 チームの位置付け

| チーム | 位置付け                              |
| ------ | ------------------------------------- |
| A      | 競技力強化・公式戦の主力候補          |
| B      | 実践力向上・Aチームへのステップアップ |
| C      | 基礎能力の習得・成功体験の蓄積        |

### 5.2 初期判定基準

| チーム |      総合得点 |
| ------ | ------------: |
| A      | 80.0〜100.0点 |
| B      |  60.0〜79.9点 |
| C      |  20.0〜59.9点 |

上記の閾値は初期運用時の暫定値とする。

実際の選手の評価結果や評価制度の妥当性を検討し、必要に応じて管理画面から変更できるものとする。

評価者数が不足している場合は判定を行わず、未判定として表示する。

### 5.3 チーム編成

自動判定による推奨チームと、実際の所属チームは別のデータとして管理する。

管理者は以下を考慮し、実際の所属チームを決定できる。

- 総合得点
- カテゴリ別得点
- ポジション
- 出席状況
- チーム全体のバランス
- 選手の育成方針
- コーチ間の協議結果

ポジションおよび出席状況は初期リリースではコーチの判断材料とし、専用の管理機能は設けない。

推奨チームと異なるチームを設定する場合、理由の入力を必須とする。

公式戦の出場選手は本システムによって自動決定しない。

### 5.4 チーム変更履歴

所属チームの変更履歴を保存する。

以下のような履歴を確認できるものとする。

- 2026年6月：Cチーム
- 2026年8月：Bチーム
- 2026年10月：Bチーム
- 2026年12月：Aチーム

A/B/Cへの固定的な所属や、チームごとの人数比率の強制は行わない。

- 簡潔なアプリケーション説明

未登録アカウントの場合はアクセス権がない旨を表示する。

チームロゴが未支給の場合はテキストによる仮ロゴを使用する。

### 7.2 SCR-02：ダッシュボード

アプリケーションのホーム画面とする。

#### サマリーカード

- 在籍選手数
- Aチーム人数
- Bチーム人数
- Cチーム人数
- 未編成人数
- 最新評価の平均得点
- 実施中の評価期間

#### グラフ

- カテゴリ別のチーム全体平均
- 評価期間ごとの平均得点推移
- 過去から現在までのチーム構成推移

#### その他

- 現在実施中の評価
- 評価入力が必要な選手

- 前回評価からの成長状況
- 評価入力へのショートカット

#### 表示項目

- 在籍状態フィルタ
- 各項目によるソート
- 選手詳細への遷移

### 7.4 SCR-04：選手詳細

本システムの主要画面とする。

#### 基本情報

- 選手名
- 背番号
- 学年
- 現在の所属チーム
- 最新の総合得点
- 前回評価との差分
- 評価実施回数

#### レーダーチャート

4カテゴリの評価を表示する。

各カテゴリの得点を100%に正規化し、カテゴリ配点の違いによる視覚的な偏りをなくす。

以下の系列を切り替えまたは重ね合わせて表示できるものとする。

- 最新評価
- 前回評価
- 初回評価
- 所属グループの平均

9項目を1〜5点で比較する詳細レーダーチャートも表示可能とする。

#### 成長グラフ

評価期間ごとの総合得点を折れ線グラフで表示する。

- 横軸：評価日
- 縦軸：総合得点
- 縦軸範囲：0〜100点
- A判定閾値
- B判定閾値
- 各評価時点のツールチップ

カテゴリ別の得点推移も切り替えて表示できるものとする。

評価基準が変更された時点には注釈を表示する。

評価基準に互換性がない場合は、単純な前回差分を表示しない。

#### 評価項目詳細

9項目について以下を表示する。

- 最新評価
- 前回評価
- 差分
- 評価基準
- 評価者数

#### コーチコメント

評価期間ごとに以下を表示する。

- 強み
- 改善点
- 自由記述
- 評価者

コメントは権限を持つ関係者のみ閲覧可能とする。

#### 評価履歴

- 評価期間
- 総合得点
- カテゴリ別得点
- 推奨チーム
- 評価者数
- 評価基準バージョン

#### チーム編成履歴

所属チームの変更を時系列で表示する。

### 7.5 SCR-05：選手登録・編集

入力項目：

- 選手名または表示名
- 背番号
- 所属学年グループ
- 入団日
- 在籍状態

選手名と所属グループを必須項目とする。

退団時は原則として在籍状態を変更し、通常の選手一覧から除外する。

選手IDは自動生成する。

### 7.6 SCR-06：評価期間一覧

過去および現在の評価期間を一覧表示する。

表示項目：

- 評価期間名
- 対象グループ
- 開始日
- 終了日
- 対象選手数
- 評価完了選手数
- 評価進捗率
- 評価基準バージョン
- ステータス

評価期間の状態：

- 下書き
- 実施中
- 確定済み

管理者のみ評価期間を作成できる。

### 7.7 SCR-07：評価期間詳細

#### 評価進捗

- 対象選手数
- 自分の評価完了数
- 自分の未評価数
- 自分の下書き数
- 必要評価者数を満たした選手数
- 評価不足の選手数

#### 選手一覧

各選手について以下を表示する。

- 選手名
- 背番号
- 自分の評価状態
- 提出済み評価者数
- 最終更新日
- 評価入力ボタン

管理者は全体の進捗および提出済み評価結果を確認できる。

一般コーチには評価期間の確定前に他のコーチの点数を表示しない。

他の評価者の点数に影響されず、独立した評価を行うためである。

#### 評価確定

管理者が評価結果を確定する。

評価不足の選手がいる場合は警告を表示する。

管理者の明示的な確認により評価期間を確定できるが、評価不足の選手は未判定とする。

確定後は評価内容を通常操作で変更できないものとする。

訂正が必要な場合は管理者が訂正用評価期間を作成し、元の評価結果を保持する。

### 7.8 SCR-08：評価入力

スマートフォンでの操作性を最も重視する画面とする。

グラウンドで片手操作しながら評価することを想定する。

#### ヘッダー

- 選手名
- 背番号
- 評価期間名
- 現在の入力進捗
- 前の選手・次の選手への移動

#### 評価入力

カテゴリごとに評価項目をグループ化する。

各項目に以下を表示する。

- 項目名
- 評価内容
- 1〜5点の選択ボタン
- 未評価状態
- 評価基準の参照ボタン

評価ボタンは十分なタップ領域を持つ横並びのボタンとする。

数値を直接入力する必要はない。

初期状態では点数を未選択とする。

すべての項目に3点等の初期値を自動設定しない。

#### コメント入力

- 強み
- 改善点
- その他コメント

各項目は任意入力とする。

#### プレビュー

入力済みの項目をもとに現在の評価状況を表示する。

全項目の入力が完了した段階で総合得点とカテゴリ別得点を表示する。

#### 保存操作

- 下書き保存
- 評価提出
- 保存して次の選手へ

保存ボタンはスマートフォン画面下部に配置する。

未保存の状態で画面遷移する場合は確認を表示する。

保存失敗時は入力値を保持し、再試行可能とする。

提出済み評価を変更した場合は評価状態を下書きに戻し、再提出を要求する。

### 7.9 SCR-09：評価結果一覧

評価期間単位で確定評価の集計結果を表示する。

#### テーブル

- 選手名
- 総合得点
- 技術力
- 判断力
- 対人能力
- 試合関与
- 前回評価との差分
- 推奨チーム
- 実際の所属チーム
- 評価者数
- 評価のばらつき

評価者数が不足している場合は未判定とする。

#### グラフ

- 総合得点分布
- カテゴリ別平均点
- A/B/C推奨チーム人数
- 前回評価との比較
- 評価者間のばらつき

管理者は評価結果をCSV形式でエクスポートできる。

CSV出力時は数式インジェクション対策を実施し、個人情報を含むファイルであることを警告する。

### 7.10 SCR-10：チーム編成

A、B、Cの3チームと未編成の選手を表示する。

PCではチームごとにカラムを分けたボード形式とする。

スマートフォンではタブ形式で切り替える。

各選手カードには以下を表示する。

- 選手名
- 背番号
- 総合得点
- 前回評価との差分
- 推奨チーム
- 現在の所属チーム

管理者は選手の所属チームを変更できる。

チーム変更はセレクトメニュー等による明示的な操作とする。

ドラッグ＆ドロップは初期リリースでは必須としない。

変更内容および理由を保存し、履歴として蓄積する。

### 7.11 SCR-11：評価基準設定

管理者専用画面とする。

設定項目：

- 評価カテゴリ
- カテゴリ配点
- 評価項目
- 項目説明
- 1〜5点の評価基準
- A判定閾値
- B判定閾値

カテゴリ配点の合計が100点となることを検証する。

変更時は既存評価基準を上書きせず、新しいバージョンを作成する。

評価開始時に使用する基準バージョンを固定する。

過去の評価結果を新しい評価基準で自動的に再計算しない。

### 7.12 SCR-12：コーチ管理

管理者専用画面とする。

機能：

- コーチ登録
- メールアドレス登録
- ロール設定
- 担当学年設定
- アカウント無効化

最後の有効な管理者を無効化できないようにする。

### 7.13 SCR-13：システム設定

管理者専用画面とする。

設定内容：

- チーム名
- 所属学年グループ
- 評価制度の初期設定
- 評価進捗の既定値
- アプリケーションバージョン
- バックエンド接続状態

## 8. グラフ・データ可視化仕様

グラフはRechartsおよびshadcn/ui Chartを使用する。

独自のCanvas描画やSVGグラフ実装は原則として行わない。

| 可視化内容           | グラフ形式                         |
| -------------------- | ---------------------------------- |
| 選手のカテゴリ別能力 | Radar Chart                        |
| 9項目の評価比較      | Radar Chart / Horizontal Bar Chart |
| 総合得点の成長履歴   | Line Chart                         |
| カテゴリ別の成長履歴 | Line Chart                         |
| チーム編成比率       | Donut Chart                        |
| チーム編成の推移     | Stacked Bar Chart                  |
| 総合得点の分布       | Histogram相当のBar Chart           |
| カテゴリ別平均点     | Bar Chart                          |
| 評価の進捗状況       | Progress Bar                       |
| 項目ごとの前回比較   | Grouped Bar Chart                  |

グラフの共通仕様：

- レスポンシブ対応
- ツールチップ
- 凡例
- 必要に応じた系列の表示切り替え
- 欠損データの明示
- 色だけに依存しない情報伝達
- アクセシビリティを考慮した数値表示
- データがない場合のEmpty State
- 不必要な3D表現や装飾を使用しない

総合得点の時系列グラフの縦軸は原則として0〜100に固定する。

過度に変化を強調する軸設定を避ける。

## 9. UI/UXデザイン仕様

### 9.1 デザインコンセプト

Light / Clear / Chic / Minimal

明るく、クリアで、シックなデザインとする。

少年サッカー向けのアプリケーションであっても、子供向けのポップなデザインにはしない。

現代的なSaaSの管理画面、スポーツ分析ツール、ミニマルなダッシュボードを参考とする。

コーチが日常的に使用する業務ツールとしての視認性、情報密度、操作性を重視する。

### 9.2 カラーパレット

以下を初期デザイントークンとする。

| 用途             | カラー  |
| ---------------- | ------- |
| ページ背景       | #F7F8FA |
| カード背景       | #FFFFFF |
| メインテキスト   | #18212B |
| サブテキスト     | #6B7280 |
| ボーダー         | #E5E7EB |
| プライマリ       | #214E48 |
| プライマリホバー | #193E39 |
| アクセント       | #527D74 |
| 成功・上昇       | #25805A |
| 警告             | #B7791F |
| エラー           | #B94A48 |

深みのあるグリーンを基調とし、サッカーを想起させながらも落ち着いた配色とする。

派手な原色、多用されたグラデーション、過剰な影、ネオンカラーを使用しない。

### 9.3 チーム識別色

| チーム | カラー  |
| ------ | ------- |
| A      | #315C91 |
| B      | #568477 |
| C      | #8A8497 |
| 未判定 | #9CA3AF |

チーム識別色を成功・失敗の色と混同しない。

Cチームに赤色を割り当てるなど、能力の否定的な印象を与える表現を避ける。

色に加えてA、B、Cのラベルを必ず表示する。

### 9.4 タイポグラフィ

- 欧文：Interまたはシステムフォント
- 日本語：Noto Sans JPまたはシステムフォント
- 数値：等幅数字を優先
- 基本文字サイズ：14〜16px
- ページタイトル：24〜28px
- セクションタイトル：16〜20px
- 主要なKPI数値：28〜36px

Webフォントを使用する場合は、可能な限りセルフホストする。

大きな数値、余白、細いボーダーによって情報の階層を表現する。

### 9.5 コンポーネント

shadcn/uiの以下のコンポーネントを積極的に利用する。

- Sidebar

- Dialog

- Sheet

- Dropdown Menu
- Input
- Textarea

- Calendar

- Progress
- Skeleton
- Separator
- Breadcrumb
- Chart
- Sonner

Lucide Reactによる統一された線画アイコンを使用する。

独自コンポーネントの作成は業務固有のUIに限定する。

### 9.6 PCレイアウト

- 左側に固定または折りたたみ可能なサイドバーを配置
- 上部にページヘッダーを配置
- メインコンテンツを右側に表示
- ダッシュボードはレスポンシブなグリッドレイアウト
- 左右の余白を十分に確保

サイドバーの幅は220〜240px程度とする。

### 9.7 スマートフォンレイアウト

スマートフォンを主要な操作端末として扱う。

- 320px以上の画面幅に対応
- 390px前後を主要設計幅とする
- 下部ナビゲーションまたはドロワーメニューを使用
- 評価入力画面では固定フッターを使用
- タップ領域は原則44px以上
- 横スクロールを極力発生させない
- ホバー操作を必須としない
- iOS SafariのSafe Areaに対応する

下部ナビゲーションの候補：

- ホーム
- 選手
- 評価
- チーム
- その他

### 9.8 余白・形状

- 4pxまたは8px単位のスペーシング
- カードの角丸：8〜12px
- ボタンの角丸：6〜8px
- 控えめなシャドウ
- 細いボーダーによる領域分割

### 9.9 インタラクション

- 画面遷移は簡潔にする
- 操作結果をSonnerによるToastで通知する
- データ取得中はSkeletonを表示する
- データが存在しない場合はEmpty Stateを表示する
- 重要操作には確認ダイアログを表示する
- 二重送信を防止する
- エラー時に入力内容を失わない
- アニメーションは100〜200ms程度を基本とする
- prefers-reduced-motionに対応する

## 11. 履歴管理

以下の履歴を蓄積する。

- 選手の評価履歴
- カテゴリ別得点履歴
- 項目別得点履歴
- コーチ別の提出評価
- コーチコメント
- チーム編成履歴
- 評価基準の変更履歴
- 管理者の操作履歴

学年が進級しても、同一選手の成長履歴を継続して参照できるものとする。

過去の評価結果は評価実施時点の基準とともに保持する。

## 12. 非機能要件

### 12.1 想定規模

初期運用：

- 選手数：20〜50名
- コーチ数：3〜10名
- 年間評価回数：8〜12回程度

将来の拡張目標：

- 選手数：200名程度
- 複数学年
- コーチ数：30名程度
- 複数年度の評価履歴

将来規模でGASやGoogle Sheetsの性能上の問題が発生した場合に、データベースおよびバックエンドを移行可能な設計とする。

### 12.2 パフォーマンス

- 通常時の画面表示は3秒以内を目標とする。
- 通常時の評価保存は3秒以内を目標とする。
- GASのコールドスタート等による遅延時はローディング状態を明示する。
- 一覧表示で選手ごとに個別APIを発行しない。
- 必要に応じてキャッシュ、ページネーションを使用する。

### 12.3 対応環境

- iOS Safari
- Android Chrome
- Windows Chrome
- Windows Edge
- macOS Safari
- macOS Chrome

原則として現行の主要ブラウザを対象とする。

### 12.4 言語

日本語を初期対応言語とする。

内部の型名、変数名、API名等は英語とする。

## 13. モックモード

バックエンドを用意していない状態でもフロントエンドの開発および動作確認が可能なモックモードを実装する。

以下の架空データを用意する。

- 選手：30名
- コーチ：4名
- 評価期間：6回分
- 評価結果：複数コーチによる評価
- A/B/Cチーム
- 成長傾向の異なる選手
- 評価不足の選手
- 評価者間のばらつきが大きい選手
- チーム変更履歴

ダミーデータは固定シードを使用して再現可能とする。

モックモードで主要な画面および操作を確認できるものとする。

モック環境であることを画面上に明示する。
