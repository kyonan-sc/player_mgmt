# 境南SC 選手評価管理システム — 技術仕様書

## 1. プロジェクト概要

### 1.1 プロジェクト名

- 日本語名：境南SC 選手評価管理システム
- 英語名：Kyonan SC Player Assessment
- リポジトリ名：`player-assessment`

### 1.2 目的

少年サッカーチームにおける選手の能力評価、成長履歴の蓄積、チーム編成の判断を支援するWebアプリケーションを開発する。

小規模なスポーツ団体による長期運用を想定し、以下を重視する。

- 原則として無料枠で運用可能であること
- 特定の開発者やコーチの個人アカウントに依存しないこと
- スマートフォンおよびPCから利用可能であること
- メンテナンスおよび機能追加が容易であること
- 選手の個人情報を適切に保護すること

## 2. システムアーキテクチャ

以下の3層構成とする。

- Presentation Layer：GitHub Pages
- Application Layer：Google Apps Script（GAS）
- Data Layer：Google Sheets

認証にはGoogle Identity Servicesを利用する。

フロントエンドからGASのWeb AppエンドポイントにHTTPSリクエストを送信し、GASを介してGoogle Sheetsの読み書きを行う。

フロントエンドからGoogle Sheetsへの直接アクセスは禁止する。

独立した常駐サーバーは設置しない。

## 4. アカウントおよびリソース管理

### 4.1 GitHub

境南SCが管理する無料のGitHub Organizationを使用する。

Organization名の候補は `kyonan-sc` とする。

GitHub FreeでPagesを利用するため、リポジトリはPublicとする。

ソースコード以外の機密情報、選手情報、評価データ、認証情報をリポジトリに含めない。

本番URLの例：

`https://kyonan-sc.github.io/player-assessment/`

### 4.2 Google

境南SCが管理するGoogleアカウントの下に以下を作成する。

- Google Driveのプロジェクトフォルダ
- Google Apps Scriptプロジェクト
- Googleスプレッドシート
- Google Cloudプロジェクト
- Google OAuthクライアント

Google側のリソースはチーム管理用アカウントが所有する。

一般のコーチは各自のGoogleアカウントでアプリケーションにログインする。

管理用アカウントのパスワードを全コーチで共有しない。

多要素認証、アカウント復旧手段、管理者交代時の引き継ぎ手順を整備する。

将来的にGoogle Workspaceの共有ドライブ等に移行可能な構成とする。

## 6. 設計・実装方針

### 6.1 基本原則

- UI、業務ロジック、データアクセスを分離する。
- Single Responsibility Principleを遵守する。
- 過度な抽象化や不要なデザインパターンの導入を避ける。
- コンポーネントに複雑な業務ロジックを記述しない。
- API呼び出しをコンポーネント内に直接記述しない。
- スプレッドシートへの直接アクセスはRepository層に限定する。
- 評価計算は副作用のない純粋関数として実装する。
- フロントエンド側の計算結果をバックエンドが無条件に信用しない。
- TypeScriptのstrictモードを有効にする。
- 原則としてany型を使用しない。

### 6.2 命名規則

- Reactコンポーネント・型・クラス：PascalCase
- 関数・変数：camelCase
- React Hooks：useから始まるcamelCase
- 定数：UPPER_SNAKE_CASE
- ディレクトリ名：kebab-case
- コンポーネントファイル名：PascalCase.tsx
- その他のファイル名：kebab-case.ts

### 6.3 状態管理

TanStack QueryをAPI由来のデータ管理に使用する。

Zustandは画面間で共有するUI状態等に限定する。

同じデータをTanStack QueryとZustandの両方で管理しない。

フォームの入力状態はReact Hook Formで管理する。

## 7. 認証・認可

### 7.1 認証方式

Google Identity ServicesによるGoogleログインを採用する。

ユーザー登録を自由に行える仕様にはしない。

事前に登録されたコーチのみが利用可能とする。

### 7.2 認証フロー

1. フロントエンドでGoogleログインを実行する。
2. GoogleからID Tokenを取得する。
3. APIリクエスト時にID TokenをGASへ送信する。
4. GAS側で署名および各種クレームを検証する。
5. Googleアカウントのsubとコーチマスタを照合する。
6. アカウントの有効性および権限を確認する。
7. 認可された場合のみデータアクセスを許可する。

### 7.3 トークン検証

バックエンドでは以下を必ず検証する。

- Google公開鍵による署名
- 署名アルゴリズム
- issuer（iss）
- audience（aud）
- 有効期限（exp）
- Googleアカウント識別子（sub）
- メールアドレスの検証状態（email_verified）

Googleの公開鍵は有効期限を考慮してキャッシュする。

未知のkidを受信した場合は公開鍵を再取得する。

本番環境ではGoogleのtokeninfoエンドポイントを認証基盤として使用しない。

JWT署名検証には既存ライブラリを利用し、暗号処理を独自実装しない。

ID Tokenは原則としてメモリ内に保持し、localStorageには保存しない。有効期限切れの場合は再認証を要求する。

### 7.4 コーチの登録

管理者がコーチのGoogleアカウントを事前登録する。

初回ログイン時に検証済みメールアドレスと登録情報を照合し、Googleのsubを紐付ける。

通常のログインではsubをユーザー識別子として使用する。

### 7.5 権限

以下の3種類のロールを定義する。

| ロール | 権限                                 |
| ------ | ------------------------------------ |
| admin  | 全機能、ユーザー管理、設定、評価確定 |
| coach  | 選手閲覧、評価入力、自分の評価の編集 |
| viewer | 許可された範囲のデータ閲覧のみ       |

認可はすべてバックエンド側で実施する。

学年・所属単位のアクセス制御も実施する。

## 8. API仕様

### 8.1 通信方式

GAS Web Appの制約を考慮し、単一エンドポイントへのPOSTによるRPC形式を採用する。

リクエストには以下のプロパティを含める。

- action：実行するAPI操作名
- requestId：リクエスト識別子
- idToken：認証用Google ID Token
- payload：操作固有のデータ

GASのdoPostでリクエストを受け取り、actionに対応する処理へディスパッチする。

Content-Typeは `text/plain;charset=UTF-8` とし、ボディにJSON文字列を格納する。

CORSプリフライトを回避するため、Authorization等の独自HTTPヘッダーを使用しない。

Content Serviceによるリダイレクトを考慮する。

fetchのmodeはcorsとし、credentialsはomitとする。

no-corsによる実装は禁止する。

### 8.2 GASデプロイ設定

- 実行ユーザー：チーム管理用アカウント
- アクセス可能ユーザー：Anyone
- アプリケーション独自の認証・認可を必須とする

GASのエンドポイント自体は公開されるが、認証・認可に成功しない限り保護された操作およびデータ取得を許可しない。

### 8.4 レスポンス

レスポンスは共通形式とする。

- success：処理成功の真偽値
- data：成功時のデータ
- error：失敗時のエラー情報
- requestId：リクエスト識別子

errorにはcodeおよびmessageを格納する。

GASでは任意のHTTPステータスコードを設定できない制約があるため、HTTPステータスだけでなくレスポンスボディによるエラー判定を行う。

エラーコード例：

- UNAUTHENTICATED
- FORBIDDEN
- VALIDATION_ERROR
- NOT_FOUND
- CONFLICT
- RATE_LIMITED
- INTERNAL_ERROR

内部エラーのスタックトレースや機密情報をクライアントに返却しない。

### 8.5 通信検証

実装の初期段階で実際のGitHub PagesとGAS間の通信を検証する。

Chrome、Safari、iOS Safariにおいて以下を確認する。

- CORS
- Content Serviceのリダイレクト
- Googleログイン
- ID Token検証
- 認証済みAPI呼び出し
- スプレッドシートへの読み書き

実運用環境で通信が成立しない場合は、セキュリティを緩和して回避しない。API中継層の追加またはGAS HTML Serviceへの変更を検討し、設計変更として承認を得る。

## 9. データベース仕様

### 9.1 基本方針

Googleスプレッドシートを簡易リレーショナルデータベースとして使用する。

1シートを1テーブルとして扱う。

1行目をカラム名、2行目以降をレコードとする。

- 主キーにはUUIDを使用する。
- 行番号をレコード識別子として使用しない。
- 外部キーの整合性はアプリケーション側で保証する。
- 日時はISO 8601形式で保存する。
- 表示時のタイムゾーンはAsia/Tokyoとする。
- 評価済みデータの物理削除を通常操作として提供しない。
- テーブル定義をコードで管理する。
- シート初期化・マイグレーション用スクリプトを用意する。

## 10. データ整合性・パフォーマンス

- 書き込み処理にはLockServiceを使用する。
- ロック取得後に一意性および更新バージョンを再確認する。
- 二重送信による重複登録を防止する。
- 重要な更新操作を冪等にする。
- 更新競合を検出し、CONFLICTを返す。
- getValues、setValues等による一括読み書きを優先する。
- セル単位の大量アクセスを避ける。
- マスタデータ等にCacheServiceを活用する。
- データ更新時は関連キャッシュを無効化する。
- 評価確定処理では結果の一意性を保証し、途中失敗後の再実行で復旧可能とする。
- Google Sheetsにトランザクション機能がないことを考慮する。
- GASのクォータおよび同時実行数を考慮する。
- 自由記述をスプレッドシートの数式として解釈させない。

## 11. セキュリティ・個人情報保護

本システムでは児童の個人情報および能力評価を取り扱う。

以下を必須とする。

- Google Sheetsを一般公開しない。
- 全APIで必要な認証・認可を実施する。
- ユーザーのロールおよび担当グループを確認する。
- スプレッドシートID等はGASのScript Propertiesで管理する。
- APIリクエストをZodで検証する。
- ID Tokenをログ出力しない。
- 実データをテストデータとして使用しない。
- ブラウザの永続ストレージに選手情報をキャッシュしない。
- ログアウト時に認証情報とAPIキャッシュを破棄する。
- 第三者向けアクセス解析を標準では導入しない。
- 不要な住所、電話番号、生年月日等を収集しない。
- Publicリポジトリへの個人情報のコミットを禁止する。
- 保護者への説明、データ保存期間、退団時の取り扱いを運用開始前に定める。
- 管理者による個人情報削除・匿名化の手順を別途用意する。

フロントエンドのURLやJavaScriptを非公開にすることをセキュリティ対策とみなさない。

## 12. 開発環境・環境変数

以下の3環境を用意する。

| 環境       | 用途                       |
| ---------- | -------------------------- |
| mock       | ローカル開発・ダミーデータ |
| staging    | 実GASを使用した結合テスト  |
| production | 本番運用                   |

stagingとproductionはGASプロジェクトおよびスプレッドシートを分離する。

### フロントエンド環境変数

- VITE_APP_ENV
- VITE_API_URL
- VITE_GOOGLE_CLIENT_ID
- VITE_USE_MOCK

VITE\_で始まる環境変数は公開情報として扱う。

### GAS Script Properties

- APP_ENV
- SPREADSHEET_ID
- GOOGLE_CLIENT_ID
- BOOTSTRAP_ADMIN_EMAIL
- SCHEMA_VERSION

claspの認証情報、OAuthクライアントシークレット等をコミットしない。

## 13. ビルド・デプロイ

### 13.1 フロントエンド

GitHub Actionsを使用する。

Pull Request時に以下を実行する。

1. pnpm install
2. lint
3. typecheck
4. test
5. build

mainブランチへのマージ後に本番用ビルドを実施し、GitHub Pagesへデプロイする。

GitHub PagesのプロジェクトURLを考慮し、Viteのbaseを設定する。

React RouterはHashRouterを使用し、直接アクセスおよびリロード時の404を回避する。

### 13.2 バックエンド

TypeScriptをGAS V8で実行可能な形式にバンドルする。

doGet、doPost等のGASエントリーポイントをグローバル関数として公開する。

claspを使用して対象のGASプロジェクトへアップロードする。

初期フェーズでは管理者による手動デプロイを採用する。

本番環境ではバージョン付きデプロイを使用する。

既存の本番デプロイを更新し、API URLを維持する。
